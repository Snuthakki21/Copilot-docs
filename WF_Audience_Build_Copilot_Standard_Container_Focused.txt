SECTION 7 — CONTAINER AND GRAIN RULES — REQUIRED TEACHING FRAMEWORK
================================================================================

This is the highest-priority build discipline in this standard. Copilot must not treat containers as a formatting detail. Containers are how the build protects the business meaning of the audience.

Plain-English rule:
A container should hold facts that must all be true about the same real-world object. A real-world object can be a customer, household, account, product, card, loan, mortgage, application, transaction, event, campaign interaction, consent record, eligibility record, or destination activation record.

Why same-container logic matters:
- It prevents false positives where one condition is true for one account/event and another condition is true for a different account/event.
- It makes the audience match the campaign manager's real business intent.
- It makes QA easier because each container has one business purpose.
- It makes the build explainable: “these fields stay together because they describe the same account,” or “these fields stay separate because they describe different steps/events.”
- It reduces bad targeting, bad suppressions, and compliance mistakes caused by mixing grains.

Important distinction:
- Folder path tells the builder where to find the attribute.
- Grain tells the builder what object the attribute describes.
- Container placement should be based on grain/object/definition/ID, not folder name alone.

Copilot must output this explanation for every container:
1. What business object does this container represent?
2. Which fields are inside it?
3. Why must these fields be evaluated together?
4. What false positive or false negative would happen if they were separated?
5. Could any field safely move to another container? If yes, why? If no, why not?
6. Plain-English explanation for campaign managers.

7.1 SAME-CONTAINER DECISION TEST
Use this test before building any logic.

Put fields in the SAME container when the answer is YES to one or more of these questions:
- Do these fields need to describe the same account, card, loan, mortgage, business, product, application, transaction, event, campaign interaction, consent record, or eligibility record?
- Does the requirement use language like “the account must be,” “that product must have,” “the same card,” “the same transaction,” “the same application,” “within the same campaign,” or “the same event”?
- Would separating the fields allow a customer to qualify because Condition A is true on one record and Condition B is true on another record?
- Is there an ID, object path, array element, or nested object that ties the fields to one record? Example: account ID, card ID, application ID, event ID, transaction ID, campaign ID, offer ID.
- Are close/status/role/date fields intended to qualify the same product/account as the product type or product code?

Use DIFFERENT containers when the answer is YES to one or more of these questions:
- Are the conditions intentionally about different objects? Example: has an open checking account but does not have a credit card.
- Are the conditions different steps in a journey or funnel? Example: email sent, then opened, then application started.
- Is one condition a global/profile-level suppression that should apply to the whole customer regardless of product? Example: deceased, privacy opt-out, global do-not-contact.
- Is one condition channel consent/preference that should be applied at profile/channel level rather than buried inside product ownership logic?
- Is one condition a household-level condition and another a person/account-level condition?
- Is the business asking for “any qualifying account” plus “no disqualifying account/product,” which requires separate positive and negative containers?

7.2 CAMPAIGN MANAGER EXPLANATION TEMPLATE
For each container, Copilot must produce a version a non-technical campaign manager can understand:

“Container [ID] groups [fields] because they all need to describe the same [business object]. We are doing this so a customer only qualifies when [business meaning]. If these fields were separated, a customer could incorrectly qualify because [specific false-positive example]. This container protects the campaign from targeting the wrong customers by enforcing [same account / same card / same event / same application / same transaction / same consent scope].”

Example for account ownership:
“Account Container A1 groups product type, account status, close indicator, relationship role, and account ID because they all need to describe the same account. We are doing this so a customer only qualifies if they personally have an open qualifying account. If these fields were separated, a customer could qualify because they have a checking account on one record and an open indicator on a different account. This protects the campaign from targeting someone who does not actually have the intended open product.”

7.3 SAME ACCOUNT / PRODUCT CONTAINER RULE
If the requirement says a customer must have a specific account or product with certain properties, place these fields in the same account/product container when available and dictionary-supported:
- Product type.
- Product code.
- Account type.
- Account status.
- Account close indicator.
- Account open date.
- Account close date.
- Ownership/relationship role.
- Account identifier.
- Product line / sub-product.
- Balance condition when it must refer to the same account.
- Delinquency/restriction/charge-off flags when they must refer to the same account.

Correct pattern:
A1{
  product_type = Checking
  AND account_status = Open/Active
  AND account_close_indicator = N
  AND relationship_role IN Owner/Primary/AuthorizedAllowedValue
  AND account_id exists
}

Risky pattern:
P{product_type = Checking}
AND P{account_close_indicator = N}
AND P{relationship_role = Owner}

Why risky: the product condition, close indicator, and relationship role may describe different accounts for the same customer.

Campaign manager explanation:
“We are keeping product type, open/closed status, close indicator, and role together because the campaign is not just asking whether the customer has any checking product somewhere and any open account somewhere. It is asking whether the same checking account is open and the customer has the correct role on it.”

7.4 ACCOUNT CLOSE INDICATOR GUARDRAIL
For active product ownership, account close indicator must not float outside the product/account container. It is usually a qualifier on the same account/product being targeted, not a generic profile fact.

Use account close indicator only after validating from the dictionary:
- Exact valid values.
- Null meaning.
- Whether it is current or historical.
- Whether it applies to all products or only certain account types.
- Whether close date is also required.
- Whether account status is the preferred open/closed indicator.
- Whether the indicator is account-level, product-level, card-level, loan-level, or derived.

Potential active account pattern:
A1{product_type/product_code = Required Product
  AND account_status = Active/Open approved value
  AND account_close_indicator = Not Closed approved value
  AND relationship_role = qualifying owner/primary role
  AND account_id exists
}

Do not assume account_close_indicator = N means open unless the dictionary says so. Do not assume null means not closed. If null meaning is missing, mark NEEDS_NULL_RULE.

7.5 SAME CARD CONTAINER RULE
For credit card audiences, card product, card account status, card close indicator, role, card/account ID, rewards/product family, delinquency, charge-off, balance, and open/close dates must be grouped when they qualify the same card/card account.

Correct pattern:
CARD1{card_product_code = TargetCard
  AND card_account_status = Open/Active
  AND card_close_indicator = NotClosed
  AND relationship_role IN approved qualifying roles
}

Wrong pattern:
P{card_product_code = TargetCard}
AND P{card_account_status = Open}

Reason: the customer may have the target card closed but a different card open.

7.6 SAME LOAN / MORTGAGE CONTAINER RULE
For loan, mortgage, home lending, auto, personal loan, student loan, or line-of-credit logic, group product type, loan status, close/payoff/maturity status, account/loan ID, borrower role, origination date, payoff date, delinquency, and balance when they describe the same loan.

Use separate containers if the campaign intentionally compares different products, such as “has open checking and does not have mortgage.”

7.7 SAME APPLICATION CONTAINER RULE
Application status belongs in an application container with product/application type, application date, channel, decision status, and application ID when they describe the same application.

Correct pattern:
APP1{application_product = Credit Card
  AND application_status = Started
  AND application_date >= today-30
  AND application_id exists
}

Reason: this prevents qualifying a customer who started one product application and had a decision/status on a different application.

7.8 SAME EVENT / BEHAVIOR CONTAINER RULE
If the requirement says a customer did a behavior in a channel/campaign/time window, place event type, campaign, channel, timestamp, offer, page, placement, and event metadata in the same event container.

Correct pattern:
EV1{event_type = Email Open
  AND campaign_id = X
  AND event_date >= today-30
}

Risky pattern:
P{event_type = Email Open}
AND P{campaign_id = X}
AND P{event_date >= today-30}

Why risky: the customer may have opened a different campaign and had a separate event in the required time window.

7.9 EVENT SEQUENCE RULE
If order matters, use sequence logic or clearly state that the build surface must support ordered event logic. Do not collapse ordered journey steps into one event container unless the same event truly contains all fields.

Example sequence:
EV1{email_sent campaign X within 30 days}
THEN EV2{email_open campaign X after EV1}
THEN EV3{application_started after EV2}

Why different containers are beneficial here:
Each event is a different real-world action. Combining them into one event container could wrongly require one event record to be simultaneously “sent,” “opened,” and “application started,” which may be impossible. Separate sequence containers preserve the journey order.

If sequence is not supported in the build surface, output NEEDS_SEQUENCE_SUPPORT_CONFIRMATION.

7.10 SAME TRANSACTION CONTAINER RULE
Transaction amount, merchant/category, transaction date, transaction channel, debit/credit indicator, posting status, and transaction ID must be in the same transaction container when they describe the same transaction.

Correct pattern:
TXN1{transaction_category = Dining
  AND transaction_amount >= 100
  AND transaction_date >= today-30
}

Reason: this prevents qualifying a customer because they had a dining transaction on one date and a $100 transaction on another date.

7.11 CAMPAIGN HISTORY CONTAINER RULE
Campaign sent/open/click/responded, campaign ID, offer ID, channel, placement, response type, and date must be grouped together when they describe the same campaign interaction.

Use separate containers for different campaign interactions or sequence steps. Example: sent in one container, clicked after sent in another container, converted after click in another container.

7.12 CONSENT / PREFERENCE / PRIVACY CONTAINER RULE
Consent must be applied at the correct channel and scope.

Examples:
- Email marketing permission for email audience.
- SMS marketing permission for SMS audience.
- Direct mail eligibility for direct mail.
- Phone permission for outbound calling.
- Global do-not-contact suppression when applicable.

Why consent may be separate:
Consent often applies to the customer/channel, not to one account. If the campaign is “open checking customers eligible for email,” the checking ownership belongs in A1 and email permission belongs in CONS1. Do not bury customer-level email consent inside the account container unless the dictionary proves consent is account-specific.

Correct pattern:
A1{product_type = Checking AND account_status = Open AND account_close_indicator = NotClosed}
AND CONS1{email_marketing_permission = True}
AND NOT SUPP1{global_do_not_contact = True}

7.13 SUPPRESSION / EXCLUSION CONTAINER RULE
Suppressions must be scoped to the thing being suppressed.

Profile-level suppressions usually sit outside product containers:
AND NOT SUPP1{deceased_indicator = True OR global_do_not_contact = True}

Product/account-level exclusions need their own product/account container when they are about the existence of a disqualifying account/product:
AND NOT A2{product_type = Credit Card AND account_status = Open AND account_close_indicator = NotClosed}

Why separate containers are beneficial here:
For “has checking but not credit card,” checking and credit card are different products. Putting both in one account container would ask for one account to be both checking and credit card, which is usually wrong. Separate containers let the build say: include customers with qualifying checking; exclude customers with a qualifying credit card.

7.14 HOUSEHOLD CONTAINER RULE
Use household conditions only when the requirement explicitly targets household-level qualification or suppression.

Examples where household may be valid:
- Household has existing relationship.
- Household-level suppression.
- Household-level exposure cap.
- Household income/segment when approved and explicitly household-scoped.

Do not use household product ownership when the requirement says the individual customer must own the product.

7.15 PERSON / PROFILE CONTAINER RULE
Use profile/person conditions for customer-level facts:
- Customer type.
- Customer status.
- Geography/state, when allowed.
- Channel consent/preference when stored at profile level.
- Global suppression.
- Deceased indicator.
- Digital enrollment if defined at profile level.

Benefit of separate profile container:
Profile facts apply to the customer as a whole. Keeping them separate from account/event containers prevents accidental interpretation that they are tied to a specific account or event.

7.16 BUSINESS / SMALL BUSINESS CONTAINER RULE
For small business or commercial audiences, confirm whether the requirement targets:
- The individual person.
- The business entity.
- The relationship between the person and business.
- A business account/product.

Group business product type, business account status, business account close indicator, business role/authority, business ID, and account ID when they describe the same business account relationship.

Use separate containers when the campaign requires a person-level qualification plus a business-level qualification.

7.17 SAME FOLDER DOES NOT AUTOMATICALLY MEAN SAME CONTAINER
Do not group attributes together only because they live in the same Audience Manager/AEP folder. A folder can contain multiple grains, old/new versions, derived fields, traits, or similar-sounding attributes.

Before same-container grouping, Copilot must prove:
- Same object/grain.
- Compatible source system.
- Compatible refresh cadence.
- Compatible current/historical meaning.
- Compatible ID/path/object relationship.
- No deprecated or test-only flag.

7.18 DIFFERENT FOLDER DOES NOT AUTOMATICALLY MEAN DIFFERENT CONTAINER
If the dictionary proves attributes describe the same object and the build surface supports grouping them, fields from different folders may still belong in the same logical container.

Example: account product code may live in one folder and account relationship role may live in another folder, but both may describe the same account relationship. Copilot must explain the evidence before grouping them.

7.19 CONTAINER DECISION MATRIX
Copilot must use this matrix in the output when there is any possible ambiguity.

| Requirement Type | Preferred Container Strategy | Why | Risk If Wrong |
| --- | --- | --- | --- |
| Active ownership of one product | Same account/product container | Product, status, close indicator, role, and ID must describe the same product/account | Customer qualifies from mixed accounts |
| Has Product A but not Product B | Product A include container plus separate Product B exclusion container | A and B are different products/accounts | One impossible container or missed exclusion |
| Email open for campaign X in last 30 days | Same event/campaign container | Event, campaign, and date must describe the same interaction | Open, campaign, and date may come from different events |
| Sent then opened then applied | Separate ordered event/application containers | Different journey steps require sequence | One event wrongly required to be all steps |
| Channel consent | Separate consent/profile container unless account-specific | Consent scope is usually customer/channel | Consent incorrectly tied to one account |
| Global suppression | Separate profile suppression container | Applies to entire customer | Suppression may only exclude one product instead of whole customer |
| Transaction behavior | Same transaction container | Amount, category, date, channel must describe one transaction | Mixed transactions qualify customer incorrectly |
| Household targeting | Household container, plus person/account containers as needed | Household facts are not individual facts | Wrong person targeted based on household member data |

7.20 REQUIRED CONTAINER QA CHECKS
Copilot must include these checks before finalizing:
- Does every account/product container include the status/close/role fields needed to prove active qualifying ownership?
- Is account close indicator inside the same container as the account/product it qualifies?
- Are all event date/time filters inside the event container they qualify?
- Are campaign ID and offer ID inside the campaign/event container they qualify?
- Are suppressions scoped correctly: profile, account, product, household, event, or destination?
- Are Product A inclusions and Product B exclusions separated when they describe different products?
- Are fields grouped because of dictionary-proven grain, not just folder proximity?
- Does every container have a plain-English “why” that a campaign manager can understand?
- Would a sample customer with multiple accounts/events accidentally qualify because of cross-object mixing?

SECTION 8 — STANDARD DESIGN PATTERNS
================================================================================

PATTERN 1 — ACTIVE PRODUCT OWNER
Use when requirement says: “customers with active [product/account].”

Logic template:
P{customer_status = eligible/active if required}
AND A1{product_type/product_code = target product
       AND account_status = open/active approved value
       AND account_close_indicator = not closed approved value
       AND relationship_role = qualifying relationship approved value}
AND CONS{channel permission = allowed if activation channel is known}
AND NOT SUPP{global/channel/product suppressions}

Required dictionary proof:
- Product code/type mapping.
- Account status values.
- Close indicator values.
- Relationship role values.
- Grain/account ID.

PATTERN 2 — HAS PRODUCT A BUT NOT PRODUCT B / CROSS-SELL
Use when requirement says: “customers with A who do not have B.”

Logic template:
A1{Product A active/open ownership logic}
AND NOT A2{Product B active/open ownership logic}
AND CONS{channel permission}
AND NOT SUPP{suppression rules}

Important:
- Product A and Product B are separate containers.
- Do not use NOT inside the Product A container unless the business requires same-account absence.
- Include close/status logic in both A and B containers.

PATTERN 3 — SUPPRESSION AUDIENCE
Use when requirement says: “exclude customers who...”

Logic template:
Base inclusion
AND NOT SUPP1{deceased/restricted/fraud/legal/privacy/do-not-contact}
AND NOT SUPP2{already has target product when cross-sell}
AND NOT SUPP3{recently contacted or offer conflict}
AND NOT SUPP4{ineligible status/channel/product}

Important:
- Suppressions must be explicit.
- Each suppression must have source field, path, value, and reason.

PATTERN 4 — RECENCY / FREQUENCY BEHAVIOR
Use when requirement says: “did X in the last N days at least M times.”

Logic template:
EV1{event_type = X
    AND event_date >= today-N
    AND event_channel = required channel if applicable
    AND campaign_id/offer_id = required campaign if applicable
    AND frequency >= M if supported}

Important:
- Date must be in same event container as behavior.
- Frequency must be attached to the relevant behavior, not global unless intended.

PATTERN 5 — LIFECYCLE STATUS
Use when requirement says: “new customer,” “tenured customer,” “new account,” or “opened account recently.”

Logic template:
A1{target product active/open
    AND account_open_date between required dates
    AND account_close_indicator = not closed approved value}

Important:
- Customer tenure and account tenure are different.
- Use customer start date for customer-level tenure.
- Use account open date for product/account-level tenure.

PATTERN 6 — DIGITAL ENGAGEMENT
Use when requirement says: “online/mobile active customers.”

Logic template:
P{digital_enrollment_status = enrolled approved value}
AND EV1{digital_login/app_use event within required window if behavior is required}
AND CONS{channel permission}

Important:
- Enrollment is not the same as recent usage.
- Mobile enrollment is not always the same as online banking enrollment.

PATTERN 7 — CAMPAIGN CONTACT HISTORY / FATIGUE
Use when requirement says: “exclude customers contacted recently” or “customers who received/opened/clicked campaign X.”

Logic template:
AND NOT CAM1{contact_channel = required channel
             AND contact_date >= today-N
             AND campaign/offer category = relevant value}

For engagement:
CAM1{campaign_id = X AND event_type = Open/Click/Sent AND event_date >= today-N}

Important:
- Campaign ID, event type, and event date must stay together.

PATTERN 8 — APPLICATION FUNNEL
Use when requirement says: “started application but did not complete.”

Logic template:
APP1{application_product = target product
     AND application_status = Started/In Progress approved value
     AND application_date >= today-N}
AND NOT APP2{application_product = target product
             AND application_status = Completed/Approved/Booked approved value
             AND application_date/completion_date >= today-N or relevant window}

Important:
- Application product, status, and date must be in the same application container.

PATTERN 9 — BALANCE / ACTIVITY THRESHOLD
Use when requirement says: “balance greater than X” or “transaction amount/frequency.”

Account balance pattern:
A1{product/account = target
    AND account_status/close indicator = open
    AND balance_amount >= X
    AND balance_as_of_date current/relevant if available}

Transaction pattern:
TXN1{transaction_type/category = X
     AND transaction_amount >= Y
     AND transaction_date >= today-N}

Important:
- Balance threshold must apply to the same account/product.
- Transaction threshold must apply to the same transaction set.

PATTERN 10 — GEOGRAPHY / MARKET ELIGIBILITY
Use when requirement has state, region, branch market, DMA, ZIP, or offer geography.

Logic template:
P{customer_state/ZIP/market = allowed value}
AND ELIG{offer geography allowed if defined separately}

Important:
- Mailing address geography and servicing address geography may differ.
- Use the geography required by the campaign and channel.

PATTERN 11 — CHANNEL ELIGIBLE AUDIENCE
Use when the output is for a specific activation channel.

Email:
CONS{email_marketing_permission = allowed value}
AND P{valid_email_indicator = true/valid approved value if required}
AND NOT SUPP{email_do_not_contact or global_do_not_contact}

Direct Mail:
CONS{direct_mail_permission = allowed value}
AND P{valid_mailing_address = true/valid approved value if required}
AND NOT SUPP{direct_mail_do_not_contact or global_do_not_contact}

SMS:
CONS{sms_marketing_permission = allowed value}
AND P{valid_mobile_phone = true/valid approved value if required}
AND NOT SUPP{sms_do_not_contact or global_do_not_contact}

Digital/App:
P{digital/mobile eligibility/enrollment if required}
AND CONS{digital marketing permission if applicable}

PATTERN 12 — EXISTING CUSTOMER BASE AUDIENCE
Use when requirement says: “all eligible Wells Fargo customers” or “existing customers.”

Logic template:
P{customer_status = active/eligible approved value}
AND P{customer_type = required type if specified}
AND NOT SUPP{deceased/restricted/fraud/global do-not-contact/other baseline suppressions}
AND CONS{channel permission if activation}

Important:
- Customer-level active is different from account-level active.
- Do not assume active customer means active target product.

PATTERN 13 — MUTUALLY EXCLUSIVE CAMPAIGN CELLS
Use when a campaign requires control/test cells or multiple treatments.

Logic template:
Base audience
AND cell assignment rule
AND NOT other cell assignment rules

Required output:
- Cell logic.
- Mutual exclusion proof.
- Randomization or prioritization method if available.

PATTERN 14 — REUSABLE BASE + CAMPAIGN-SPECIFIC LAYER
Use for clean maintainable builds.

Base audience:
P{active eligible customer}
AND NOT SUPP{baseline suppressions}
AND CONS{channel permission}

Campaign layer:
A/EV/APP/CAM specific qualification.

Benefit:
- Easier QA.
- Reusable suppressions.
- Easier count waterfall.

SECTION 9 — COMMON WELLS FARGO MARKETING SUPPRESSIONS TO CHECK
================================================================================

Do not apply these blindly. The requirement, channel, policy, legal/compliance guidance, and dictionary must support them. However, Copilot must check whether the requirement needs these suppressions:

Customer/person suppressions:
- Deceased indicator.
- Global do-not-contact.
- Channel-specific opt-out.
- Invalid channel address or phone/email.
- Restricted customer status.
- Legal, privacy, or regulatory suppression.
- Fraud/security restriction where applicable.
- Employee exclusion if campaign requires it.
- Minor/age restriction if product or channel requires it.
- Non-US or unsupported geography if campaign requires it.

Account/product suppressions:
- Closed account.
- Charged-off account.
- Delinquent account where product/policy requires exclusion.
- Account restriction/hold/block.
- Non-qualifying relationship role.
- Already owns target product for acquisition/cross-sell.
- Product-specific ineligibility.

Campaign/contact suppressions:
- Contacted in last N days.
- Received same offer recently.
- Already responded/converted.
- Holdout/control group.
- Offer conflict.
- Frequency cap.

Channel suppressions:
- Email opt-out / invalid email.
- SMS opt-out / invalid mobile / unsupported SMS consent.
- Direct mail opt-out / invalid address.
- Phone opt-out / do-not-call.
- Paid media activation restrictions.

Compliance reminder:
For financial-services marketing, protected-class, sensitive, creditworthiness, adverse-action, fair-lending, privacy, consent, and eligibility rules may require legal/compliance review. Copilot must flag these as review items, not invent policy.

Candidate comparison table:

4. Clear valid values.

SECTION 12 — QA STANDARD
================================================================================

Every audience must have QA before activation.

12.1 COUNT WATERFALL
Output a count waterfall even if actual counts are unavailable. If counts are not available, create the rows and mark Count = TBD.

Required steps usually include:
1. Starting population.
2. Customer/profile eligibility.
3. Product/account inclusion.
4. Event/behavior inclusion.
5. Product/account exclusion.
6. Campaign/contact suppression.
7. Consent/channel suppression.
8. Global/legal/privacy suppression.
9. Destination eligibility.
10. Final audience.

12.2 COUNT SMELL TESTS
Flag these issues:
- AND condition increases count.
- Suppression increases count.
- OR condition decreases count unexpectedly.
- Final audience is larger than starting population.
- Closed account suppression removes zero records when closed accounts are expected.
- Channel opt-out removes zero records for channel activation.
- Product ownership count is much higher/lower than historical expectations.
- Null handling changes count dramatically.
- Duplicate records inflate count because account-level rows are not deduplicated to profile/person level.
- Exclusion has no effect because it is scoped to the wrong container.

12.3 TEST CASES
At minimum, create:
- Positive profile: should qualify.
- Negative profile: missing required product.
- Negative profile: has target product but account is closed.
- Negative profile: has product but non-qualifying relationship role.
- Negative profile: opted out of channel.
- Negative profile: deceased/global suppression.
- Edge profile: multiple accounts where one qualifies and one does not.
- Edge profile: null close indicator/status.
- Edge profile: recently contacted or already converted if campaign suppressions apply.

12.4 SAMPLE PROFILE REVIEW
For sample records, verify:
- Profile/person ID.
- Account ID(s).
- Product code/type.
- Account status.
- Account close indicator.
- Relationship role.
- Channel consent.
- Suppression indicators.
- Whether qualification is correct.

SECTION 17 — DO / DO NOT RULES
================================================================================

DO:
- Use the data dictionary first.
- Validate grain before logic.
- Keep same-object facts in the same container.
- Use exact folder paths.
- Use exact valid values.

- Do not assume product code mappings.
- Do not assume null means false/no/open/eligible.

- Do not use event dates outside the event container.
- Do not use consent for one channel as permission for another channel.
- Do not hide exclusions inside a vague phrase like “standard suppressions.”
- Do not call a build final if folder paths or valid values are missing.
- Do not use sensitive/protected/creditworthiness variables without explicit approved requirement and compliance review.
- Do not over-nest containers when simple logic works.

SECTION 22 — CONTAINER EXPLANATION MINI-GUIDE FOR LEARNING
================================================================================

Use this section to learn from each build. Copilot must include a learning summary that answers these questions:

1. What is the main business object of the audience?
Examples: customer, account, card, mortgage, application, event, transaction, campaign response.

2. Which attributes had to stay together?
Example: product type, account status, close indicator, role, and account ID.

3. Why did they have to stay together?
Because the audience requirement is about the same account/product. Separating them can qualify a customer using facts from different accounts.

4. Which attributes were intentionally separate?
Examples: profile-level consent, global suppressions, Product B exclusions, event-sequence steps.

5. Why were they separate?
Because they describe a different object or a broader rule. For example, email consent applies to the customer/channel, not to one checking account. A credit card exclusion is a different product from a checking-account inclusion.

6. What should I tell the campaign manager?
Use this wording:
“We grouped the account/product fields together so the audience qualifies customers based on the same qualifying account, not by accidentally combining facts from different accounts. We kept consent and global suppressions separate because those apply to the customer/channel overall. We used separate exclusion containers for products we are trying to exclude because those products are different objects from the product we are including.”

7. What should I check next time?
- Is this a profile, household, account, product, card, loan, application, transaction, event, campaign, consent, or destination requirement?
- Do all fields inside a container describe the same object?
- Does account close indicator qualify the same account/product as product type and account status?
- Are event dates in the same event container as the event they filter?
- Are exclusions scoped to the thing being excluded?
- Can I explain the grouping in one sentence to a campaign manager?

Required final learning sentence:
“The reason this build is structured this way is: [plain-English reason connecting requirement, dictionary fields, containers, suppressions, and QA].”
